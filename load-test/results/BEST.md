# 위험 서비스 검증·측정 상태

## 현재 코드 판정

기능 정확성과 성능 인증을 분리합니다. 안정화 작업 소스는 132개 테스트,
Spotless, Checkstyle을 통과했습니다. 예약 생성은 한 번의 Redis Lua 연산으로 만료
정리, 요청 지문 재실행 검사, 확정액과 예약액을 합친 한도 검사, 예약 기록을
수행합니다.

현재 소스로 예약 경로나 진단용 확인 경로의 지연 시간·지속 처리량을 재측정하지
않았습니다. 따라서 현재 코드의 RPS, p95/p99, 최대 사용자 수 또는 Kafka 소비
처리량을 제시하지 않습니다.

## 현재 정확성 검증

- 마지막 남은 한도에 대한 20개 동시 요청 중 한 건만 예약됩니다.
- 동일 betId와 동일 요청 지문으로 100회 요청해도 예약은 한 건입니다.
- 다른 요청 지문은 충돌하며 해제, 만료, 확정 뒤의 합계가 일치합니다.
- 기존 `bet.placed.v1` 재전달은 확정 집계와 패턴 이력을 중복 반영하지 않습니다.

이 항목들은 기능과 원자성에 대한 검증이며 처리량 측정으로 해석하지 않습니다.

## 안정화 전 측정 자료

날짜별 디렉터리의 모든 결과는 현재 안정화 전 소스 또는 별도 패치 후보에서
생성됐습니다. 변경 전후 비교와 측정 도구 보존용이며 현재 코드의 대표 수치가
아닙니다.

- `2026-05-29/`: 초기 진단 API와 합성 Kafka 발행 측정
- `2026-07-13/`: 당시 소스에 적용한 별도 패치 후보
- `2026-07-14/`: 스냅샷 구현 후보와 통과 조건 확인

특히 `2026-05-29/consumer_throughput.txt`는 유효한 Avro 이벤트를 소비시키지 않은
합성 바이트를 발행한 결과입니다. 발행부터 브로커 확인까지 걸린 시간을 잰 것이므로
risk-service의 소비 처리량을 보여 주지 않습니다.

## 다시 측정할 때

현재 소스와 공통 계약의 커밋 SHA를 고정하고 초기화한 Redis·Kafka에서 예약 경로를 포함해
다시 측정해야 합니다. Kafka 수치는 유효한 Avro 이벤트, 브로커 확인, 소비 지연과
최종 Redis 반영을 함께 확인해야 소비 처리량으로 기록할 수 있습니다. 카운터는
KRW만 검증했으므로 다른 통화의 안전성 또는 용량 근거로 사용하지 않습니다.
